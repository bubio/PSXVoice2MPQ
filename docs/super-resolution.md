# 音声超解像（VoiceFixer / ONNX）仕様

**結論**: AudioSR を廃止し、VoiceFixer を ONNX 化したモデルを ONNX Runtime でアプリ内から直接推論する。ユーザーに Python は要求しない。
モデルは前段（ファイル全体、GRU を含む）と後段（畳み込みのみ）の 2 グラフに分ける。長いファイルも、後段を文脈付きの区間に分けてそのままつなぐだけで、全体を一度に処理した結果と一致する。クロスフェードは使わない。リサンプリング（soxr_hq 相当）もグラフに含める。
VoiceFixer は低域まで作り直すので、子音やアタックが欠ける。このため、出力のうち 4.8kHz 以下を元の音声に差し替え、VoiceFixer からは高域だけを使う（聴き比べで採用）。
実行環境はローカル（ONNX Runtime、Dart FFI）と Google Colab（同じ ONNX モデルを GPU で実行し、zip で受け渡し）から選べる。FlashSR は検証してから追加する。

変換スクリプトとリファレンス実装: `tools/voicefixer_onnx/`（M4 の CPU で、STREAM5 の 732 ファイル・約 2 時間分が 63 分。ピークメモリは 3.7GB 以下）

---

## 全体の流れ

```
[抽出] STREAM → VAG → WAV(11kHz)                          ← 既存処理
   │
   ├─ ローカル: ONNX Runtime で推論（Isolate 内）──────┐
   │                                                 ▼
   └─ Colab:  エクスポート(zip) → ノートブック → インポート(zip)
                                                     ▼
                     超解像キャッシュ（モデル・入力ハッシュで管理）
                                                     ▼
[ビルド] キャッシュがあれば 44.1kHz に差し替え → MP3 → MPQ   ← 既存処理
```

- 対象はこれまでと同じく、map に載っている WAV だけ（1 言語あたり約 730 ファイル、約 2 時間分）。
- キャッシュがないファイルは元の 11kHz WAV のまま使い、ログに件数を出す。ビルドは止めない。

## モデル

| グラフ | 入力 → 出力 | 処理 | サイズ |
|---|---|---|---|
| `vf_front.onnx` | `wav11k` [1,1,n]（11025Hz、-1.0〜1.0）→ `unet_in` [1,2,T,128]、`orig44k` [1,1,4n] | soxr_hq と同じ 4 倍アップサンプル（6638 タップの FIR）→ STFT → mel → 雑音除去（双方向 GRU） | 38MB |
| `vf_back.onnx` | `unet_in` [1,2,Tc,128] → `wav44k` [1,1,Tc×441+1764] | UNet → ボコーダ（どちらも畳み込みのみ） | 394MB |
| `vf_post.onnx` | `orig44k`, `vf44k` [1,1,4n] → `wav44k` [1,1,4n] | 4.8kHz 以下を元の音声に差し替え: `vf + LP(orig − vf)`（線形位相 FIR 1023 タップ） | 4KB |

元の重みは VoiceFixer（コードは MIT、重みは CC-BY-4.0, Haohe Liu）。

### アプリ側の処理（`pipeline.py` の `restore()` を Dart に移植する）

1. 前段を、ファイル全体に対して 1 回実行する（95 秒のファイルでも 0.3GB）。
2. 後段: T ≤ 3072 フレーム（約 30.7 秒）なら一括で実行する。それより長い場合は、区間 1536 フレームに前後 768 フレームの文脈を付けて実行する（境界は 64 フレーム単位）。各結果から文脈の部分を捨ててそのままつなぐ。最後の区間は末尾まで残す。
3. 結果をつないだ出力の、1244 サンプル目から 4n サンプルを切り出す（固定遅延）。
4. 後処理グラフに、前段が出力した `orig44k` と、3 の結果を渡す。
5. ファイル全体のピークが 1.0 を超えたら正規化する。

- 分割した場合も、全体を一度に処理した結果との一致は SNR 75〜86dB。後段に一度に渡す長さを 3072 フレームまでにしているのは、3584 フレームでメモリが 3.3GB から 5.3GB に跳ねるため。
- 本家の中央トリム（出力長と入力長の差の半分を捨てる）は、入力長によって 2〜7ms ずれる。分割すると切れ目で音が欠けたり重なったりするので使わない。このため、出力は本家と比べて一定の時間ずれる（音質は変わらない）。
- 30 秒を超えるファイル（stream5 では 39 個）は、文脈の分だけ計算量が約 1.9 倍になる。
- `tools/voicefixer_onnx/export.py` でモデルを作り、`pipeline.py` がリファレンス実装。Python が必要なのは、開発者がモデルを作り直すときだけ。

### 配布

- 3 つの ONNX ファイルは、このリポジトリの GitHub Releases に置く（タグ `model-data-voicefixer-1`。プレリリース扱いで Latest にはしない。ビルド用ワークフローは `v` で始まるタグのリリースでだけ動く）。アプリには同梱しない。
- 初めて超解像を有効にしたときにダウンロードする。進捗を表示し、途中から再開できるようにし、SHA-256 で検証してからアプリのデータディレクトリに置く。
- 重みのライセンス（CC-BY-4.0）の表記は、アプリの「ライセンス」画面と Releases の説明に載せる。

## ONNX Runtime の組み込み

- ONNX Runtime の C API を `dart:ffi` から呼ぶ。バインディングは `tool/ffigen_onnxruntime.dart` で `third_party/onnxruntime/onnxruntime_c_api.h` から生成する（`lib/src/third_party/onnxruntime.g.dart`）。
- 同梱には Dart の native assets を使う。`hook/build.dart` が、ターゲットの OS と CPU に合った公式リリースのアーカイブ（1.23.2、macOS・Windows・Linux の x64 と arm64）をダウンロードし、固定した SHA-256 で検証してから、ライブラリを code asset として登録する。Flutter がこれを各 OS のアプリに同梱する（macOS のリリースビルドではユニバーサルバイナリになる）。Xcode のプロジェクトファイルや CMake は変更しない。
- オフラインでビルドするときは、user define の `onnxruntime_library` で、展開済みのライブラリを指定する。
- 実行プロバイダは CPU だけにする（CoreML は可変長入力でモデル構築に失敗した。CUDA や DirectML は配布サイズが増えるので見送る）。
- 推論は専用の Isolate で 1 ファイルずつ行う。セッションは 1 つ作って使い回す。スレッド数は ONNX Runtime の既定（物理コア数）にする。
- キャンセルは、メインの Isolate から `OrtRunOptions` の terminate フラグを立てて行う（実測では 4ms で止まる）。結果は一時ファイルに書いてからリネームするので、キャンセルしても書きかけのキャッシュは残らない。

## 設定

`settings.json` に保存する。旧 `audioSr*` キーは読まずに削除する。

| キー | 値 | 既定 |
|---|---|---|
| `sr.engine` | `none` / `voicefixer` | `none` |
| `sr.backend` | `local` / `colab` | `local` |

- エンジンを `none` 以外にしたときだけ backend を表示する。local でモデルがまだない場合は、ダウンロードボタンとサイズ（3 ファイルで計 432MB）を表示する。
- 所要時間の目安を表示する（ローカル CPU で、音声の長さの約半分。M4 で 1 言語あたり約 1 時間）。
- 超解像が有効なときの MP3 品質（`-V 4`）は現行のまま。AudioSR 用だった「VAG→WAV 変換時の gain 2.0」は廃止する（VoiceFixer の本家は gain をかけない）。

## キャッシュ

`<cacheDir>/sr/<モデルID>/<入力WAVのSHA-256>.wav`

- モデル ID は固定の文字列 `voicefixer-v1`（`SuperResolutionService.modelVersion`）。モデルを作り直したときはこれを変えて、古いキャッシュを使わないようにする。毎回 432MB のハッシュを計算しないための判断。
- 入力のハッシュをキーにするので、言語（STREAM）が違っても同じ音声なら再利用できる。
- 現行の「ビルドが成功したらキャッシュを消す」動作はやめる。削除は、設定画面に既存の「キャッシュを削除」ボタンで行う。
- キャッシュは入力の内容をキーにしているので、いつ再利用しても正しい。そのため、ビルド開始時の「中断データが見つかりました（続きから再開／最初からやり直す）」ダイアログは廃止する。中断したビルドは、もう一度ビルドすれば終わったところから自動で続く。

## Colab 連携

1. アプリで「Colab 用にエクスポート」を実行する。抽出だけを行い、`sr_input.zip`（対象の WAV と `manifest.json`）を書き出す。
2. アプリが表示するリンクからノートブックを開く: `https://colab.research.google.com/github/bubio/PSXVoice2MPQ/blob/v<アプリのバージョン>/colab/super_resolution.ipynb`
3. ノートブックは `onnxruntime-gpu` と、アプリと同じ ONNX モデルを使う。zip をアップロードし、実行し、`sr_output.zip` をダウンロードする。
4. アプリで「Colab の結果をインポート」を実行する。`manifest.json` のモデル ID と各ファイルのハッシュを確認してから、キャッシュに入れる。

```json
{"appVersion":"1.1.0","modelId":"3f2a9c...","files":[{"name":"J0079.WAV","sha256":"..."}]}
```

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| ユーザーが用意した Python 環境でエンジンを動かす | 環境構築のハードルが高い（今回の目的） |
| `uv` で Python 環境を自動構築する | PyTorch で数 GB になる。ARM64 版 Windows で動くかが不確実 |
| PyInstaller でまとめた実行ファイルを配布する | 6 つの OS・CPU の組み合わせごとに、GB 単位のファイルをビルドする必要がある |
| リサンプリングをアプリ側で行う（既存の Lanczos(a=5)） | 聴き比べで soxr_hq より劣った。LSD も約 7dB 違う |
| libsoxr を FFI で同梱する | 4 倍の変換は FIR 1 本で完全に再現できる（SNR 131dB）ので不要 |
| VoiceFixer の出力をそのまま使う | 低域まで作り直されるので、子音やアタックが欠けて聞き取れなくなる箇所がある（J0128 では、子音帯域が悪い方から 10% の区間で -21.9dB） |
| 雑音除去部を外す | 子音の欠落は改善しなかった（欠落は UNet とボコーダで起きている） |
| 30 秒ごとに単純に分割する（本家方式） | 切れ目の前後で LSD 10〜12dB の段差が出る。言葉なのでクロスフェードでもごまかせない |
| 無音の位置で切り、区間ごとに全体を推論する | GRU がファイル全体を見ているため、区間が短くなるほど音色が全体処理からずれる |
| 分割せずにファイル全体を一度に推論する | 95 秒のファイルでメモリが 6.9GB 必要になる |
| Colab でサーバを立て、トンネル経由で呼ぶ | 無料枠の利用規約に抵触するおそれがある。トンネルのトークン管理も必要 |

## やらないこと

- AudioSR の継続サポート（コードと設定キーは削除する）
- VoiceFixer の mode 1（高域除去の前処理）と mode 2（train モード）
- GPU による実行（ローカル）
- 超解像結果のプレビュー再生や A/B 比較 UI

## 残っている課題

- 処理時間の短縮: FP16 化や量子化の効果と、音質への影響を確認する。ボコーダが処理時間の 78% を占める
- Windows と Linux の実機で速度とメモリを計測する（現在の数値は M4 の macOS のみ）
- FlashSR: ライセンスの確認と、ONNX に変換できるか。できる場合は `sr.engine` に追加する
